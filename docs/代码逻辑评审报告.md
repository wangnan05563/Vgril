# CodexQQSkin 代码逻辑评审报告

评审范围：`server.py`（静态服务 + HeyGen/腾讯智影/大模型反向代理）、`assets/js/app.js`（前端对话/数字人/创作内核桥接）、`assets/js/*.mjs` 模块化内核（接口契约抽查）。评审聚焦：整体逻辑正确性、边界与异常处理、控制流、数据结构与算法、模块依赖与接口一致性、并发/状态管理、可读性可维护性。

---

## 🔴 Critical（必须修复）

### 1. SSRF / 开放代理 + DNS 重绑定（TOCTOU）—— `server.py` `proxy_llm` / `_safe_target`

**问题**
- `llmEndpoint` 可由客户端经 `POST /api/config`（白名单 `CFG_KEYS` 含 `llmEndpoint`）写入服务端并持久化，随后服务端用该地址发起出站请求。
- `_safe_llm_endpoint` → `_safe_target` → `_assert_public_host` **先解析 DNS 并校验每个 IP 为公网**，通过后放行；但真正发请求时 `_proxy_upstream` → `_pooled_request`（`http.client.HTTPConnection(host,…)`）或 urllib **会再次解析域名**。存在 TOCTOU 窗口：校验时返回公网 IP、连接时返回私网 IP → **DNS 重绑定可绕过私网/IP 黑名单校验，打内网或云元数据（169.254.169.254）**。
- 服务绑定 `127.0.0.1`，但**任意网页（用户访问的恶意站点）都能 `fetch('http://127.0.0.1:8080/api/llm')`**（localhost 可达），因此这是一个可被远程网页利用的 localhost SSRF：恶意页可先 `POST /api/config` 把 `llmEndpoint` 指向重绑定域名，再借 `/api/llm` 做跳板。
- 默认 `_LLM_ALLOWED_HOSTS` 为空 ⇒ 等价于"允许代理到任意公网 https 主机"。

**定位**：`server.py:227-234`（`_safe_llm_endpoint`）、`server.py:560-568`（`proxy_llm` 调用 `_proxy_upstream`）、`server.py:187-209`（`_assert_public_host` 校验与连接分离）。

**改进建议**
1. **解析一次、钉死 IP**：在 `_safe_target` 解析出 IP 后，连接阶段直接连该 IP，并用 `Host` 头携带原始主机名（连接池 `_pooled_request` 已支持 `Host` 头），杜绝重绑定。
2. **默认拒绝 + 显式白名单**：`_LLM_ALLOWED_HOSTS` 默认应为非空（如 `api.deepseek.com,api.openai.com,…`），未配置时只允许预置公网白名单，禁止客户端任意写入 endpoint 域名。
3. 对 HeyGen 代理同样评估：`HEYGEN_HOST` 为服务端环境变量（非客户端可控），风险低，但建议在文档中明确其为受信任服务端配置。

### 2. 字幕/AI 水印重复写入（控制流分支重复触发 `startCap`）—— `app.js` `digitalHumanSpeak`

**问题**
`digitalHumanSpeak(text)` 在入口（line 549）调用了一次 `startCap(text)`；而它的下游分支又各自再调用一次：
- `!dh.enabled` → `speak(text)`（line 94 再次 `startCap`）
- `dh.provider==="local"` 或远端失败回退 → `localAvatarSpeak(text)`（line 516 再次 `startCap`）

结果：**本地动画与"数字人总开关关闭"两条主路径，同一句台词被 `startCap` 写入两次**。后果：
- 导出 WebVTT/SRT（`buildVTT`/`buildSRT`）出现重复字幕段；
- `window.Xiaoya.subtitle.push` 被重复推送；
- `fsPush`（全屏字幕）靠 1s 内同文去重兜底，但 `captions` 数组不去重，导出链路与内核链路不一致。

**定位**：`app.js:549`（入口）、`app.js:94`、`app.js:516`（叶子重复）。

**改进建议**（最小改动、单一真相源）
- 删除 line 94（`speak` 内 `startCap(text)`）与 line 516（`localAvatarSpeak` 内 `startCap(text)`），保留 `digitalHumanSpeak` 入口处的唯一一次 `startCap`。
- 核查：`speak` 仅被 `digitalHumanSpeak` 调用（line 551），删除其 `startCap` 不影响其它路径；`localAvatarSpeak` 仅被 `digitalHumanSpeak` 调用，删除安全。
- 远端视频成功路径（line 549 `startCap` + line 579 `endCap`）保持单对，无需改动。

## 🟡 Suggestions（应当考虑）

### 1. 缺少连接级超时 / 慢速攻击（Slow-loris）耗尽线程—— `server.py`

**问题**
- `Handler` 在 `do_POST` 中 `self.rfile.read(length)` 读取 body，但 `ThreadingHTTPServer`/` HTTPServer` **未设置 socket 超时**，连接 socket 也无 `settimeout`。若客户端声明很大 `Content-Length` 却缓慢或根本不发送，read 会一直阻塞，线程与 `_REQ_SEMA` 信号量槽位被长期占用。
- `protocol_version="HTTP/1.1"` 开启 keep-alive，但 idle keep-alive 连接同样无超时，会持续占用线程。
- 虽服务仅绑 `127.0.0.1`，但本地恶意进程/网页仍可利用，导致并发上限（256）被占满后正常请求一律 503。

**定位**：`server.py:419`（Handler 无超时）、`server.py:618-621`（`QuietHTTPServer` 仅设 `request_queue_size`/`daemon_threads`）、`server.py:486-499`（按 `Content-Length` 读取 body）。

**改进建议**
- 在 `Handler.__init__` 中 `self.connection.settimeout(30)`（或在 `QuietHTTPServer` 覆盖 `get_request` 设置超时）。
- 读取 body 前对 `Content-Length` 设上限（如 `min(length, MAX_REQUEST_BODY)`），超界直接 413。
- idle keep-alive 也可靠 `ThreadingHTTPServer` 的 `timeout` 配合 `protocol_version` 处理。

### 2. 模块加载期 `loadRemoteConfig()` 未 await，存在配置覆盖竞态—— `app.js`

**问题**
`loadRemoteConfig()` 在模块顶层（line 691）以 `async` 触发但**未 await**，后续同步代码（应用主题、绑定事件、`syncDH`/`syncLLM`）立即执行并基于 localStorage 默认值初始化；随后远程配置异步返回再回填并 `saveSettings()`。期间若用户已在界面操作，可能出现：初始界面闪烁、远程非空值覆盖本地刚刚的修改、`pushRemoteConfig()` 又反向写回形成环。

**定位**：`app.js:662-691`（定义与调用）。

**改进建议**
- 在 `window.load` 流程中先 `await loadRemoteConfig()` 完成后再初始化 UI/绑定；或用一个 `configReady` Promise 串行化首次 `syncDH`/`syncLLM` 与 `loadRemoteConfig`。
- 合并策略明确化：本地修改（用户输入）应优先于远程回填，避免"远程空值被本地非空覆盖后再被远程非空覆盖"的抖动。

### 3. 腾讯智影调用绕过代理 + 硬编码超时—— `server.py`

**问题**
`tencent_call`（line 373-384）直接用 `urllib.request.urlopen(req, timeout=90)`，**未走 `_proxy_upstream`/`_open` 代理通道**。在配置了 `HTTPS_PROXY` 的环境（项目明确支持代理，见 `_build_opener`），腾讯云调用会绕开代理而导致不可达，与 HeyGen/LLM 的代理行为不一致。

**定位**：`server.py:381-384`。

**改进建议**
- 改用 `_open(req)`（已统一处理代理与超时），并将超时纳入 `API_TIMEOUT` 或独立常量，避免硬编码 90。

### 4. `_acquire` 失败路径的 503 与信号量释放一致性（复核确认无 bug，但建议收紧）

**问题（复核结论：当前正确，仅建议）**
`do_GET`/`do_POST` 中 `if not self._acquire(): return` —— 获取失败时不进入 `try`，因此 `finally` 中的 `_release` 不会执行，信号量不被错误释放（正确）。但有一个隐含前提：`_acquire` 内部**仅在失败时**发送响应并返回 False，成功时绝不发送响应。当前实现符合，建议加注释固化该契约，防止后续误改。

**定位**：`server.py:466-480`、`server.py:481-508`、`server.py:596-606`。

### 5. 创作面板点击未对内核缺失做防御（null 调用）—— `app.js`

**问题**
`renderScenes`/`renderThemes` 中 `const st = window.Xiaoya && window.Xiaoya.studio;` 取可能为 `null`；但 `unlocked` 分支的点击回调里仍调用 `st.applyScene(...)`/`st.applyTheme(...)`（line 860、872）。若模块化内核未加载（`st===null`），用户点击会抛 `TypeError`。运行时内核通常已加载，但属脆弱点。

**定位**：`app.js:853-875`。

**改进建议**
- 点击回调前置 `if(!st){ toast("⚠️ 创作内核未加载"); return; }`，与录制/精选按钮的守卫风格保持一致（参考 line 815、827）。

### 6. `reply()` 关键词匹配过宽，误触发人设分支—— `app.js`

**问题**
吃醋分支关键词含 `"忙"`、`"她"`、`"朋友"`、`"出去玩"` 等单字/短词，极易误命中正常对话（如"你今天忙吗"→吃醋、"他说…"→吃醋）。属产品逻辑而非崩溃级 bug，但会影响"傲娇人设"的可信度。

**定位**：`app.js:190`、`app.js:194`。

**改进建议**
- 用更具体的短语/正则（如排除"他说/她是我妈"等），或引入否定词过滤；建议把关键词表外置为可配置数据，便于调参。

## 🟢 Nits（可选）

1. **死代码**：`app.js:338` `const DH_VIDEO = "";` 及其 `if(DH_VIDEO){…}` 分支永远不执行；数字人视频真正走 `digitalHumanSpeak` 远端路径。建议删除或接入设置项。
2. **`fmtTime` 小时溢出**：`app.js:112-116` 小时硬编码 `"00:"`，超过 1 小时的字幕时间戳（SRT/VTT）会失真。建议用 `getUTCHours()` 并拼接。
3. **`captions` 数组会话内无上限**：`app.js` 仅 `memory` 做了 `slice(-40)`，字幕 `captions` 随聊天累积，长会话导出体积偏大；可作为会话级状态在合适的时机清理。
4. **`build` 脚本 `$ErrorActionPreference='Stop'` 陷阱**：PyInstaller 往 stderr 写 WARNING 会被当终止错误 abort（历史已绕过，改用 `*> log`）。建议在 `build_package.ps1` 注释固化该坑，或在调用处 `2>&1` 显式吞掉 WARNING。
5. **`save_config` 读取未加锁**：`get_config`（`server.py:511`）读取 `CONFIG` 全局字典未持 `_CONFIG_LOCK`。CPython 单键操作原子，可接受，但严格意义上读写应同锁；建议读也短时间持锁或直接返回副本 `dict(CONFIG)`。
6. **`_memAdapter.put` 的 id/_id 映射**：`app.js:772-776` 外部记录用 `.id`，内部记忆用 `._id`，`MemoryStore` 走 `.id`；二者仅在经 `getAll` 时统一为 `id`。若外部经 `put({id,…})` 写入，删除时 `memory.findIndex(x=>x._id===id)` 会因 `_id` 不存在而找不到。建议 `put` 时统一 `m._id = rec.id`。
7. **`renderAIBadge` 在 `speak` 与 `digitalHumanSpeak` 双重调用**：虽为幂等（仅 add class），但属重复意图，配合 Critical#2 修复后可一并清理。

## ✅ What's Good

- **SSRF 基础防护到位**：`_assert_public_ip` 覆盖私网/环回/链路本地（含 `169.254.169.254`）/保留/组播/未指定；`_safe_target` 强制 https、拒绝 userinfo/非法端口/路径穿越。对出站目标做了系统性约束。
- **有界响应读取**：`_read_bounded` 防异常大响应拖垮本机，超限抛 `ValueError` 被统一转 502。
- **并发有界 + 快速失败**：`_REQ_SEMA` 信号量 + 0.05s 超时返回 503，避免线程无限堆积；配置文件写用 `_CONFIG_LOCK` + 原子 `os.replace` 防丢失更新/竞态。
- **目录锚定安全**：`HERE = sys._MEIPASS or 脚本目录` 并固定 `directory=HERE`，避免 `SimpleHTTPRequestHandler` 回退到 cwd 暴露源码。
- **前端密钥不落地**：HeyGen/LLM 密钥经服务端注入或仅服务端持有，前端只传文本与 Avatar/Voice ID，规避 CORS 与前端密钥泄露。
- **配置双写兜底**：localStorage + 服务端 `xiaoya_config.json`，解决跨端口/重启丢失；且 `CFG_KEYS` 白名单限制客户端只能写约定键。
- **AI 合规水印**：`renderAIBadge`（REQ-COMP-01）在语音/数字人输出时挂"由 AI 生成"，且录制时随屏捕获。
- **模块化内核桥接整洁**：`window.Xiaoya` 聚合 Voice/DigitalHuman/Subtitle/Clip/Studio/Recorder/Memory，全局名不冲突；`MemoryStore.list()` 正确将同步适配器 `getAll()` promisify，桥接契约自洽。
- **溢出/上限防御**：`memory.slice(-40)`、`fsSub` 超出 5 行渐隐移除、数字人轮询 `for i<60` 有上限不会死循环、TTS 异常有 `safety` 兜底定时器强制复位。
