## 0. 总体结论

**两份文档骨架合格，可以作为研发基线，但存在 3 类必须修补的硬伤**：

1. **隐私主张自相矛盾**（概要设计 vs 需求卖点）——"数据不出本机"只在离线/本地模式成立，启用大模型/数字人时用户对话文本实际会出境。文档把它们混为一谈，对外宣传有合规与误导风险。
2. **P0 安全机制可靠性未论证**——危机检测靠"关键词+情绪启发式"，既无评测集也无失败兜底；作为合规红线功能，漏报的法律责任未在设计中处理。
3. **安全负债未识别**——`server.py` 的 `/api/llm`、`/api/heygen` 接受客户端任意 endpoint/path 做服务端转发，是典型 SSRF/开放代理向量，两份文档均未提及。

**建议**：M0 详细设计已就位，但须在其前补一份《安全与一致性修订》再开工；M1 前须补隐私边界澄清与 LLM 输出护栏设计。总体**不建议直接据此进入编码**，先消化本报告 §3–§5 的 P0/P1 问题。

## 1. 需求规格说明书评审

### 1.1 优点（保留）
- 优先级分级（P0–P3）清晰，验收标准大多可测。
- 竞品矩阵覆盖了海外/国内/数字人三类，维度统一。
- 市场规模标注了口径差异，没有强行统一，态度严谨。
- 风险表（§9）已触及合规变化与第三方依赖。

### 1.2 问题清单（按严重度）

| # | 严重度 | 问题 | 说明 / 建议 |
|---|---|---|---|
| R1 | 🔴 高 | **市场数据无可追溯来源** | 全球 $371 亿、中国 ¥38.66 亿等均为"某报告"口径，文档未附 URL/报告名。AI 生成文档易混入不可核实数字。→ 每条补来源链接或标注"待核实"，否则 7 日留存目标等推论失去依据。 |
| R2 | 🔴 高 | **"数据不出本机"作为卖点，但需求未界定在线模式的数据出境边界** | REQ-COMP-05 只讲"不参与训练"，未讲"启用大模型/数字人时对话文本会发往第三方"。→ 在 §4.2 增加"数据流向矩阵"：明确哪些模式数据留本机、哪些出境、用户如何知情与撤回。 |
| R3 | 🟠 中 | **北极星指标缺乏论证** | "7 日留存 ≥35%"（行业 <20%）无推导路径，像拍脑袋。→ 给出基线假设（当前留存？样本？）与达成手段的逻辑链，否则无法验收。 |
| R4 | 🟠 中 | **合规映射停留在"征求意见稿"** | 国内办法是草案，正式稿条款可能变化；且未列出具体须满足的条款号（如标识位置、实名粒度）。→ 补"条款对照表（草案版）"，并标注"以正式稿为准"的切换机制。 |
| R5 | 🟠 中 | **未成年人处理策略缺失** | REQ-COMP-02 做年龄确认，但未成年"能否使用""可用到什么程度"未定义。仅"防沉迷锁定"不够——多数法规要求未成年人限制或禁止。→ 明确未成年模式的功能边界（如禁用数字人视频/限制对话深度）。 |
| R6 | 🟡 低 | **部分验收标准不可测** | "记忆：弱/中"、"情绪有可感知延续性"无量化。→ 改为可观测指标（如"跨会话召回 topK 命中率""情绪波动在 N 轮内可观测"）。 |
| R7 | 🟡 低 | **商业化（REQ-BIZ）与本地优先存在张力** | "订阅/买断"需账号与支付后端，与"零服务器"定位冲突。→ 明确增值走的还是"用户自备/本地密钥"模式，或承认需要轻量后端，避免范围蔓延。 |
| R8 | 🟡 低 | **缺少明确的"非目标/范围外"章节** | 易引发后续范围扯皮。→ 单列 §"明确不做的事"。 |

## 2. 概要设计评审

### 2.1 优点（保留）
- 分层架构把"合规/安全"作为拦截器贯穿链路，方向正确。
- 存储升级 IndexedDB、资源外置，契合本地优先。
- REQ→模块追溯矩阵（§11）便于验收追踪。
- server.py "无业务状态、密钥仅服务端"的约束守住了。

### 2.2 问题清单（按严重度）

| # | 严重度 | 问题 | 说明 / 建议 |
|---|---|---|---|
| D1 | 🔴 高 | **隐私主张与架构事实矛盾** | §2/§10 称"数据不出本机"，但 §4.4 `LLMAdapter`、§7 `/api/llm` 会把用户消息（含记忆/人设上下文）发往 OpenAI/DeepSeek；§4.6 数字人视频也出境。→ 必须区分"本地模式（真·不出本机）"与"增强模式（明示出境、最小化、可关）"，并在 UI 给用户在每轮知情。这是对外承诺的合规底线。 |
| D2 | 🔴 高 | **未识别 server.py 的 SSRF / 开放代理风险** | `proxy_llm` 读取客户端 `x-llm-endpoint` 后服务端直接请求该 URL；`proxy` 转发 `/api/heygen/*` 任意路径。攻击者可用本机服务作为跳板访问内网/元数据（如 169.254.169.254）。→ 概要设计 §10 安全项须补：endpoint 白名单/协议限制（仅 https + 已知域名）、禁止内网网段、HeyGen 路径固定化。 |
| D3 | 🔴 高 | **危机检测可靠性未论证且无失败兜底** | §4.8/§5.2 用关键词+情绪启发式，阈值 0.6 偏召回。但：① 无评测集/准确率指标；② 若检测"完全失效"（关键词库为空/未触发），没有任何兜底，等于 P0 红线裸奔；③ 漏报的法律责任未定义。→ 补"检测失败兜底"（如定期合规自检、人工接管入口常驻）、评测方案、以及"检测不可靠时的保守策略"。 |
| D4 | 🟠 中 | **单文件 vs 多文件未决** | §8/§12 对"是否拆 module 静态托管"措辞犹豫。这直接影响打包与加载性能。→ M0 前必须二选一：建议"主程序单文件 + `assets/` 资源外置静态托管"，明确打包脚本改动点。 |
| D5 | 🟠 中 | **LLM 输出护栏不足（越狱/漂移）** | §4.4 "注入 system prompt 防漂移"，但仅 SafetyFilter（关键词）过滤输出，面对越狱提示词脆弱。→ 补"输出护栏"：角色边界约束 + 违规重定向 + 关键场景（未成年/危机）硬编码拒绝，而非依赖关键词。 |
| D6 | 🟠 中 | **内容安全"价值观过滤"仅靠本地词库不现实** | §4.8/§9 把安全完全本地化。但监管要求（涉政/暴恐等）词表需持续更新，纯本地易过时；且"价值观"非关键词能覆盖。→ 明确：底线词表随包更新机制 + 承认价值观层面能力上限 + 在出境模式下借助 LLM 侧的合规（若启用）。 |
| D7 | 🟠 中 | **数字人"口型同步"名不副实** | §4.6 `fallbackCSS` 用"口型脉冲"模拟，非真实唇形同步；即便视频模式也依赖供应商是否支持。→ 文案改为"口型动画（模拟/供应商依赖）"，避免对用户的虚假承诺。 |
| D8 | 🟡 低 | **流式可打断架构未细化** | REQ-VO-02 "边生成边播放、开口即打断"需音频队列 + STT 抢占设计，概要未给。→ M1 详细设计补中断状态机。 |
| D9 | 🟡 低 | **迁移回滚的实操风险** | §6 迁移有 backup 字段，但未定义"迁移中途崩溃"的恢复路径（如半写 IndexedDB）。→ 补事务/版本校验与"启动自检修复"。 |
| D10 | 🟡 低 | **缺可访问性（a11y）与国际化** | 三栏 UI、弹窗对键盘/读屏用户、色弱友好度未提。→ 至少列为基础非功能项。 |

## 3. 关键一致性问题（跨文档）

1. **隐私口径不一致**：需求文档把"本地优先、数据不出本机"作为对外卖点（§4.2、附录 A），但概要设计实际允许启用 LLM/数字人时数据出境（D1/R2）。**对外宣传与实现必须对齐**，否则既是合规风险也是信任风险。
2. **"不参与训练"的边界模糊**：REQ-COMP-05 默认拒绝训练，但用户一旦配置第三方 LLM，对话是否参与对方训练由对方 ToS 决定，本地无法保证（D1 延伸）。需写明"本地模式保证；增强模式取决于所选服务商的隐私政策，由用户自担并知情同意"。
3. **合规"红线"与"草案"的张力**：两份文档都把合规当 P0，但依据的是征求意见稿。若正式稿要求"实名认证（非仅年龄自认）"，当前 REQ-COMP-02（自认年龄）可能不达标——需在 M0 预留实名接口位（已在风险表提及，但需在需求侧明确"自认模式为草案过渡方案"）。

## 4. 安全专项（本评审重点升级项）

| 风险 | 位置 | 等级 | 处置建议 |
|---|---|---|---|
| SSRF / 开放代理 | `server.py` `proxy_llm`（客户端 `x-llm-endpoint`）、`proxy`（任意 heygen 路径） | 🔴 高 | endpoint 限 https + 域名白名单；HeyGen 路径枚举固定；拒绝私有网段（127/10/172.16/192.168/169.254）；加请求超时与大小上限。 |
| 危机检测失效 | 概要 §4.8/§5.2 | 🔴 高 | 检测不可用时的保守兜底 + 评测集 + 法律责任边界说明。 |
| LLM 越狱/输出违规 | 概要 §4.4 | 🟠 中 | 输出护栏（角色边界 + 硬编码拒绝关键场景），不依赖关键词。 |
| 隐私出境未告知 | 需求/概要 D1 | 🔴 高 | 数据流向矩阵 + 每轮知情 + 增强模式可关。 |
| 配置/密钥误用 | `xiaoya_config.json` | 🟡 低 | 密钥不进导出包（已写），补"配置篡改检测"。 |

## 6. 结论与放行建议

- **需求文档**：可保留框架，须修 R1/R2/R3/R4/R5 后作为基线。
- **概要设计**：架构方向正确，但 **D1/D2/D3 三处硬伤不修复不应进入编码**；M0 详细设计已写，建议在其前插入《安全与一致性修订》一节消化本报告 P0 项。
- **整体放行**：当前状态 = **有条件通过（pending P0 修订）**。先补隐私边界、SSRF 加固、危机兜底三件事，再启动 M0 实现。
