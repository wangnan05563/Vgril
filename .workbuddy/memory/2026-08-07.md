## start.bat 蓝屏排查与修复
- 用户反馈：双击/运行 start.bat 导致电脑蓝屏（BSOD）。
- 排查结果：
  - `record_burn.ps1` 未被 start.bat 调用，排除。
  - `server.py` / `CodexQQSkin.exe` 仅是本地 HTTP 服务 + 自动开浏览器，纯用户态，无内核/磁盘操作，不可能直接引发 BSOD。
  - 唯一破坏性操作是旧 start.bat 第7行：`netstat -ano | findstr ":8080 " ` → `tokens=5` → `taskkill /PID %%a /F`，**无差别强制杀掉任何占用 8080 的程序**（含系统/其它应用），可能暴露第三方驱动 bug 触发内核崩溃。
  - 实际 BSOD 多为内核崩溃（内存/显卡/存储驱动/Win 更新隐患），用户态脚本通常只是巧合触发或暴露驱动缺陷。
- 修复：移除无差别强杀，改为 `taskkill /IM CodexQQSkin.exe /F`（只清理本项目自己的残留 exe，绝不误杀其它进程）；端口冲突由 server.py 既有 8080→8089 顺延兜底。已同步 root 与 dist/start.bat，并重建 `CodexQQSkin_release.zip`（7 文件）。
- 给用户补充：定位真正的 BSOD 成因需查 `C:\Windows\Minidump\*.dmp`（WinDbg/WhoCrashed）或事件查看器 System 日志的 BugCheck；若复现，重点排查内存/RAM、显卡驱动、杀软 EDR 驱动。
- 新增 `bsod_diag.ps1`（只读）：从系统日志 WER 1001 抓取最近 BugCheck、解码常见错误码含义、列出 minidump、`-Analyze` 可选调用 cdb/windbg 自动分析。纯只读，不删改系统文件。已通过 Parser 语法校验。

- 经验：Windows 批处理文件必须保持 ASCII（或显式 GBK/带 BOM UTF-8），绝不能在 .bat 里混用 UTF-8 中文。

## start.bat 第三次报错（括号陷阱）排查与修复
- 用户再次反馈运行 start.bat 报 `此时不应有 on`（本次无乱码，纯 ASCII 已确认）。

- 验证：写了纯 Python 的 cmd 感知括号解析器（不依赖子进程，沙箱会杀 cmd 子进程）确认两份文件 `block_depth_end=0` 且**无括号陷阱**；字节检查确认 BOM=False / 无非 ASCII / 全 CRLF。
